## مصدر 1: Web From Security Check.pptx

- **اسم المشروع (النظري):** Web Form Security Check
- **الطلاب:** A. Freihat, T. AL-Ramamneh, O. Bani Hamdan, Y. Albdour
- **المشرف:** Dr. Albaraa Awjan — جامعة البلقاء التطبيقية، كلية الذكاء الاصطناعي
- **الهدف:** أداة تكتشف تلقائيًا كل النماذج (forms) في موقع وتحدد المخاطر الأمنية الحرجة فيها.
- **التركيز:** غياب HTTPS، غياب Security Headers، ضعف التحقق من المدخلات (Input Validation).
- **المخرج:** تقرير بسيط يوضح النماذج غير الآمنة ومتطلبات الإصلاح.
- **أهداف المشروع:**
  - تحليل ثغرات OWASP Top 10 الحرجة.
  - بناء scanner آلي لـ SQLi وXSS وCSRF.
  - تنفيذ Passive وActive scanning.
  - نظام تقارير مفصل بمستويات خطورة.
  - الاختبار على بيئات تجريبية (DVWA).
  - واجهة فحص بضغطة واحدة (one-click scan).
  - دعم صيغ تقارير متعددة (PDF/JSON).
  - توثيق إصلاح قابل للتنفيذ (actionable remediation).
- **نطاق المشروع (Included):**
  - فحص فرض HTTPS.
  - اكتشاف Security Headers (CSP, HSTS).
  - تحديد ضعف Client-side Validation.
  - سمات Form غير آمنة (autocomplete, CSRF).
- **خارج النطاق (Excluded):**
  - تفاعل متقدم مع قاعدة بيانات من جهة الخادم.
  - Authentication bypass exploits.
  - File upload أو command injection.
  - تعديل/حذف بيانات تدخّلي (intrusive).
- **متطلبات النظام (من العرض):**
  - وظيفية: إرسال والتحقق من URL، crawler آلي لاكتشاف النماذج، ربط الثغرات بمعايير OWASP، توليد تقرير منظم.
  - غير وظيفية: أداء (فحص كامل خلال 30 ثانية)، سهولة استخدام لغير التقنيين، أمان (عدم تسجيل بيانات حساسة)، Uptime هدفه 99%.
- **معمارية النظام (Pipeline معياري):** Input Handler → Crawler Engine → Vulnerability Scanner (Active Tests) → Analysis Engine (التحقق من صحة النتائج) → Report Generator.
- **منهجية الفحص الأمني (8 خطوات):** تحديد الهدف → Crawl لاكتشاف الصفحات والنماذج → تحليل أنواع المدخلات → اختيار Payloads حسب OWASP → تنفيذ اختبارات نشطة/حقن → تحليل استجابة الرؤوس والمحتوى → التحقق من النتائج (تقليل الضجيج) → توليد تقرير قابل للتنفيذ.

## مصدر 2: نسخة من Graduation project.docx (الفصول 1-3)

### الملخص (Abstract)
كثير من المواقع تحتوي نماذج غير آمنة تعرّض بيانات المستخدم للخطر. المشروع يبني أداة تكتشف تلقائيًا
كل النماذج في موقع وتتحقق من غياب HTTPS، غياب Security Headers، وضعف التحقق من المدخلات، ثم تولّد
تقريرًا بسيطًا يوضح النماذج غير الآمنة وما يحتاج إصلاحه.

### الفصل 1: المقدمة
- **خلفية الدراسة:** النماذج (forms) وسيلة أساسية لتبادل البيانات؛ الثغرات الشائعة: غياب التشفير
  (HTTPS)، ضعف Input Validation، تخزين بيانات غير آمن، غياب الحماية من XSS وSQL Injection.
- **مشكلة البحث:** الفحص اليدوي لكل نموذج في موقع كبير غير عملي زمنيًا؛ لا توجد أداة مجانية وبسيطة
  متخصصة في crawling واكتشاف مشاكل النماذج تحديدًا.
- **أهداف المشروع:**
  1. Crawl آلي لاكتشاف الصفحات والموارد.
  2. اكتشاف واستخراج كل نماذج HTML، شاملة المحمّلة ديناميكيًا حيث أمكن.
  3. التحقق من استخدام HTTPS بدل HTTP.
  4. التحقق من وجود Security Headers أساسية (CSRF tokens, X-Frame-Options, CSP).
  5. اختبار ضعف/غياب التحقق من المدخلات عبر حقن أنماط هجوم شائعة (XSS/SQLi أساسية).
  6. توليد تقرير واضح يوضح أي النماذج غير آمنة ولماذا.
  7. توصيات قابلة للتنفيذ لإصلاح المشاكل بسرعة دون خبرة أمنية عميقة.
  8. أداة مجانية وخفيفة وسهلة الاستخدام لغير الخبراء.
- **نطاق المشروع:** يعمل على مواقع عامة لا تتطلب تسجيل دخول؛ يفحص كل نماذج HTML الموجودة؛ التركيز
  على مشاكل الواجهة الأمامية (HTTPS، Headers، Validation)؛ **لا يختبر هجمات متقدمة تحتاج وصولًا
  لقاعدة البيانات**؛ تقارير بصيغ بسيطة (HTML/JSON/CSV).
- **المنهجية المقترحة (نظريًا في الوثيقة):** Python + BeautifulSoup + Requests للـ crawling؛
  فحص الاستجابات وHeaders؛ حقن Payloads اختبارية بسيطة (XSS/SQLi/command injection) في حقول
  النماذج؛ لا يتطلب صلاحيات خاصة؛ توليد تقرير HTML آلي.

### الفصل 2: مراجعة الأدبيات
- دراسات حول أمن النماذج في بنية Client-Server، وأهمية Feature Policy وReferrer Policy رغم ضعف
  انتشارهما.
- Web Crawling الذكي لاكتشاف نقاط الإدخال تلقائيًا؛ تحديات SPA وJavaScript-rendered content.
- حماية متعددة الطبقات: تشفير قوي (TLS 1.2+)، input validation، CAPTCHA، Zero Trust (تقليل
  حركة جانبية بنسبة 72% في بيئات هجينة حسب مصدر مذكور).
- أداة WAVES (Web Application Vulnerability and Error Scanner) كمثال دراسة سابقة.
- دراسة Lavrenovs & Rubio (2018): تحليل واسع لانتشار Security Headers (CSP, HSTS,
  X-Frame-Options) على أكبر مليون موقع، وأظهرت أن كثيرًا من المواقع لا تطبقها أو تطبقها بشكل خاطئ.
- دمج SAST/DAST/IAST لتحسين دقة الاكتشاف وتقليل False Positives (Mateo Tudela et al., 2020).

### الفصل 3: التحليل والتصميم
- **تحليل النظام:** فحص آلي لثغرات النماذج ونقاط المصادقة عبر fuzzing، اختبارات حقن، وفحص Headers؛
  مطابقة الثغرات المكتشفة مع OWASP Top 10؛ تقرير نهائي بمستويات خطورة وخطوات إصلاح.
- **المتطلبات الوظيفية:** إدخال والتحقق من URL، crawl آلي (شامل JS حيث أمكن)، تطبيق حقن/fuzzing
  لاكتشاف SQLi/XSS/CSRF/Headers غير آمنة، تصنيف كل ثغرة مؤكدة ضمن OWASP Top 10، تصفية
  False-Positive، تقرير نهائي بخطورة + مكوّن متأثر + تصنيف OWASP + خطوة إصلاح.
- **المتطلبات غير الوظيفية:** أداء (فحص صفحة واحدة خلال 30 ثانية)، عدم تخزين/تسجيل/نقل بيانات
  حساسة، بيئة sandboxed معزولة، سهولة استخدام لغير التقنيين، Uptime لا يقل عن 99%، معالجة فشل
  الفحص دون فقد بيانات، دعم فحص متزامن لعدة أهداف، قاعدة بيانات ثغرات قابلة للتحديث المستقل.
- **مكوّنات التصميم:** User Interface (Web Dashboard)، Crawler Engine، Vulnerability Scanner
  (اختبارات نشطة: SQLi وXSS)، Analysis Engine (تأكيد التهديدات، إزالة التكرار، تحديد الخطورة)،
  Database (تخزين أساليب الهجوم ونتائج الفحص التفصيلية).
- **Use Case Diagram (وصف نصي):** ثلاثة actors: User، Admin، Target Web Application. وظائف:
  Login/Authenticate، Configure Scan Settings، Initiate Web Crawling، Vulnerability Scanning،
  View Real-time Scan Progress، Generate Security Reports، Manage Attack Vector Database (Admin
  فقط)، View Historical Scan Data (كلا الطرفين).
- **معمارية النظام:** المستخدم يرسل URL ويختار إعدادات الفحص عبر الواجهة → الخادم الخلفي يتحقق من
  الإدخال ويدير عملية الفحص → محرك الفحص يختبر SQLi وXSS وCommand Injection وLFI → تخزين النتائج
  والتقارير في قاعدة البيانات → توليد تقرير مفصل مع توصيات → لوحة Admin لإدارة المستخدمين والإعدادات.
- **تصميم قاعدة البيانات (نظريًا في الوثيقة):** ست جداول: `users` (حسابات وأدوار admin/user)،
  `scans` (target URL، النوع، الحالة، التوقيت)، `vulnerabilities` (الخطورة، النوع، CWE ID، خطوات
  الإصلاح)، `scan_settings` (crawl depth، active scan flag)، `reports` (مسار الملف والنوع)،
  `vuln_references` (مراجع خارجية: عنوان، رابط، مصدر).
- **الأدوات والتقنيات (نظريًا في الوثيقة):** Python 3، Django (كإطار ويب)، MySQL، محرك فحص مخصص
  لـ SQLi/XSS عبر pattern matching وpayload injection وتحليل الاستجابة، ReportLab لتوليد PDF،
  VS Code، Postman، Google Chrome. عملية اختبار: تحليل المتطلبات → تصميم حالات اختبار → إعداد
  البيئة → تنفيذ → تحقق من النتائج → تسجيل الأخطاء → إعادة الاختبار (Regression).
- **عملية الاختبار الأمني (8 خطوات موسّعة):** تحديد الهدف → crawl (صفحات، نماذج، حقول، معاملات)
  → تحليل كل مدخل (النوع، الطول، قواعد التحقق الحالية) → اختيار Payloads وفق OWASP → تنفيذ الحقن
  ومراقبة الاستجابات → تحليل الاستجابة (pattern matching/heuristics لأخطاء SQL أو تنفيذ سكربت)
  → التحقق اليدوي من النتائج الحرجة لتقليل False Positives → تقرير نهائي بخطورة (High/Medium/
  Low/Informational) + وصف + تأثير + توصية، قابل للتصدير PDF/HTML.
- **أنواع الثغرات المغطاة نظريًا:** SQL Injection (boolean-based, union-based, time-based)،
  XSS (reflected, stored, DOM-based)، Input Validation (أنواع بيانات غير صالحة، boundary
  conditions)، Security Misconfiguration (headers، directory listing، رسائل الأخطاء).
